High-level design

DevFlow OS architecture

A multi-tenant API monitoring platform: scheduled checks, incidents, alerts, error tracking and an optional AI root-cause analyst. Three views of how it fits together, then the decisions behind them.

Design decisions and what they cost

Each choice is reasonable at the current scale. The right-hand column is what to say when asked what breaks first.

DecisionWhyTrade-off
Job queue instead of timersSchedules survive restarts; retries and concurrency come built in; more workers can be added.Needs Redis. Retries currently sleep inside the job and hold a worker slot.
Workers inside the API processOne deployable unit on free tiers; shared code and connections.Cannot scale API and workers separately. Splitting them is a small change because they only meet through Redis and MongoDB.
Tenant = workspace, filter on every queryOne rule that is easy to audit and test.Relies on each controller keeping the filter. A shared query helper would remove that risk.
Embedded members, timelines, commentsRead together, no joins, one write.Not suitable for lists that can grow without limit.
TTL indexes on logs and eventsBounded storage with no cron job.Raw history lasts 30 days. No hourly or daily rollups yet.
Analytics cached for 60 sUptime is an aggregation over many rows; dashboards refresh often.Up to a minute of staleness. If Redis is down the endpoint errors instead of falling back.
AI: model suggests, code executesIds come from the database, tools are read-only, inputs are clamped, rounds are capped, a switch turns it off.Free-tier quota limits use. A diagnosis can be wrong, so it is shown with its evidence and labelled AI-generated.
